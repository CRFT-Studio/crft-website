Code splitting is the practice of dividing application code into multiple smaller files (chunks) instead of shipping one large bundle. Users download only what they need for the current route or interaction, which improves [load time](/glossary/page-load-time) and [Time to Interactive](/glossary/time-to-interactive).

## Why Code Splitting Matters

Modern frontends can grow large quickly. Without splitting, every visitor may download code for features they never use. Splitting reduces unused [JavaScript](/glossary/javascript), especially on first load.

## Common Code Splitting Strategies

### Route-Based Splitting
Each page or route loads its own chunk. This is one of the most effective defaults for multi-page and [SPA](/glossary/single-page-application) architectures.

### Component-Based Splitting
Heavy components—charts, editors, maps, [modals](/glossary/modal)—are loaded only when rendered or requested.

### Vendor Splitting
Third-party [libraries](/glossary/library) are separated into their own chunks so app updates do not force full vendor re-downloads.

## How It Works in Practice

Bundlers like Vite, Webpack, and Parcel support dynamic imports:

```javascript
const Chart = await import('./HeavyChart.js');
```

[Frameworks](/glossary/framework) often wrap this pattern with [lazy-loading](/glossary/lazy-loading) helpers so routes and components can be split with minimal boilerplate.

## Benefits

- Faster initial page loads
- Better [caching](/glossary/cache) for unchanged chunks
- Lower main-thread work on first render
- Improved [Core Web Vitals](/glossary/core-web-vitals) on JS-heavy sites

## Trade-Offs and Pitfalls

### Too Many Small Chunks
Excessive splitting can create network overhead through too many requests.

### Loading Waterfalls
Poorly planned lazy loads can delay critical [UI](/glossary/user-interface) if [dependencies](/glossary/dependencies) fetch sequentially.

### Layout Shifts and Spinners
Late-loading components need thoughtful placeholders so [UX](/glossary/user-experience) still feels stable.

## Best Practices

1. Split by route first, then target heavy components
2. Preload likely next-step chunks for smoother [navigation](/glossary/navigation)
3. Measure bundle size and real-user performance impact
4. Keep critical [above-the-fold](/glossary/above-the-fold) code in the initial path
5. Avoid lazy-loading content required for first paint

Code splitting is one of the highest-leverage [frontend](/glossary/frontend) performance techniques when applied to real user journeys rather than arbitrary file boundaries.
